

Fluent + ICU4X is a more “engineering-heavy” route than gettext, but it aligns very well with:

* Rust,
* wasm/Yew,
* structured localisation,
* long-term maintainability.

And accounting software eventually becomes more about localisation than many people expect.

A few practical observations from where you are now:

---

# 1. Treat localisation as infrastructure, not UI decoration

The temptation is to start with:

```rust
t!("menu.file")
```

But for accounting systems, localisation eventually touches:

* tax terminology,
* financial formatting,
* PDFs,
* emails,
* validation messages,
* exports,
* CSV formats,
* dates,
* decimal separators,
* audit logs,
* report layouts.

So build the plumbing properly early.

You are making the right decision.

---

# 2. Use Fluent for *messages*, not formatting

This is one of the most important architectural separations.

Good:

```rust
let amount = format_currency(locale, value);

fluent!("invoice.total", {
    "amount" => amount
});
```

Bad:

```rust
fluent!("invoice.total", {
    "amount" => raw_decimal
});
```

The translation layer should not decide:

* decimal separators,
* currency rules,
* rounding rules.

That belongs in ICU4X or your accounting logic.

---

# 3. Build a thin abstraction layer immediately

Do not scatter Fluent calls everywhere in Yew components.

Instead create something like:

```rust
pub trait I18n {
    fn text(&self, key: &str) -> String;
    fn text_args(&self, key: &str, args: FluentArgs) -> String;
}
```

Even if it feels unnecessary now.

Why:

* easier testing,
* easier SSR later,
* easier locale switching,
* easier report generation,
* easier fallback handling,
* avoids Fluent internals leaking through the whole app.

This becomes important surprisingly quickly.

---

# 4. Separate “domain terms” from sentences

This matters a lot in accounting systems.

Example:

```text
term.accounts_receivable
term.tax_invoice
term.balance_due
```

Separate from:

```text
invoice.balance_due_message
```

Because terminology changes independently of sentence structure.

Especially across:

* AU,
* NZ,
* UK,
* US,
* EU.

Even English variants differ significantly in accounting.

---

# 5. Expect locale handling to spread everywhere

You will probably eventually want:

```rust
struct UserContext {
    locale: Locale,
    timezone: TimeZone,
    currency: Currency,
}
```

because:

* reports,
* PDFs,
* dates,
* exports,
* timestamps,
* currency formatting

all depend on it.

Do not make locale a frontend-only concept.

---

# 6. PDFs are where i18n gets real

Your frontend localisation is the easy part.

The hard part becomes:

* Unicode fonts,
* RTL text,
* CJK line breaking,
* numeric alignment,
* column width expansion,
* translated report headings.

You mentioned Tryst for PDFs. Check early:

* UTF-8 support,
* embedded fonts,
* fallback fonts,
* text measurement accuracy.

You do not want to discover later that Japanese invoice rendering breaks pagination.

---

# 7. Fluent works best when translators control grammar

A common mistake is over-assembling sentences in Rust.

Bad:

```rust
format!("{} {}", t!("customer"), customer_name)
```

Good:

```fluent
customer-name = Customer: {$name}
```

This matters far more outside English.

---

# 8. Start with en-AU as a first-class locale

Not generic English.

Use:

* `en-AU`
* not `en`

Accounting terminology varies enough that this becomes worthwhile.

Later:

* `en-NZ`
* `en-GB`
* `en-US`

can inherit or override selectively.

---

# 9. Decide now how translation assets are loaded

You have two major models:

## Compile-time embedding

Using:

* `include_str!`
* embedded bundles

Pros:

* simpler deployment,
* no missing files,
* easy Docker/container deployment.

Cons:

* translation updates require rebuild.

Probably best initially.

---

## Runtime loading

Pros:

* translators can update without recompiling,
* admin-customisable wording possible.

Cons:

* more operational complexity,
* cache invalidation,
* bundle management.

You can add this later.

---

# 10. Watch wasm bundle size early

ICU4X is vastly better than old ICU, but localisation data still grows.

Be selective about:

* calendars,
* collation,
* numbering systems,
* locale datasets.

Otherwise Yew wasm size can balloon quietly.

---

# Suggested overall architecture

Something roughly like:

```text
Frontend (Yew)
    -> i18n facade
        -> Fluent bundles

Backend (Rocket)
    -> same message keys
        -> Fluent bundles

Formatting layer
    -> ICU4X

Reports/PDFs
    -> same translation service
```

Shared message keys between frontend/backend are extremely valuable.

---

# One thing I would strongly recommend

Avoid storing translated text in the database.

Store:

* semantic codes,
* enums,
* identifiers.

Translate at presentation time.

Otherwise localisation becomes almost impossible to evolve cleanly.

---

# Exceptions

* Don't translate "KelpieBooks", which is the product name.

# Final thought

The Rust i18n ecosystem still feels less polished than:

* Java,
* .NET,
* JavaScript.

But Fluent + ICU4X is probably the closest thing Rust currently has to a genuinely modern localisation architecture.

For a long-lived accounting application, it is a sensible technical direction rather than just a trendy one.
